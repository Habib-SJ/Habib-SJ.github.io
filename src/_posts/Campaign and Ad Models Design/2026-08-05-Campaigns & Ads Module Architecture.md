# سند معماری: مدل‌های Campaign و Ad

## 1. هدف

ماژول `campaigns` مسئول مدیریت کمپین‌های تبلیغاتی و تبلیغ‌های وابسته به هر کمپین در پلتفرم AdTech است. این ماژول هسته‌ی اصلی چرخه‌ی اجرای تبلیغات را تشکیل می‌دهد و امکان تعریف بودجه، بازه‌ی زمانی اجرا، وضعیت کمپین و محتوای تبلیغاتی (Creative) را فراهم می‌کند.

در این مرحله، دو موجودیت اصلی طراحی و پیاده‌سازی شده‌اند:

- `Campaign`
- `Ad`

---

## 2. ساختار اپلیکیشن

برای تفکیک مسئولیت‌ها، یک اپلیکیشن مستقل با نام `campaigns` ایجاد شده است.

```text
campaigns/
├── models.py
├── admin.py
├── migrations/
├── services.py
└── ...
```

این اپلیکیشن مسئول نگهداری مدل‌ها و منطق مرتبط با کمپین‌ها و تبلیغات است. منطق‌های تجاری پیچیده‌تر، مانند بررسی سقف بودجه یا تغییر وضعیت خودکار کمپین، در ادامه می‌تواند در فایل `services.py` پیاده‌سازی شود تا مدل‌ها صرفاً مسئول نگهداری داده باقی بمانند.

---

## 3. مدل Campaign

مدل `Campaign` نماینده‌ی یک کمپین تبلیغاتی است که توسط یک تبلیغ‌دهنده ایجاد می‌شود. هر کمپین می‌تواند دارای بودجه، بازه‌ی زمانی اجرا، وضعیت عملیاتی و چندین تبلیغ باشد.

### فیلدها

| فیلد | نوع داده | توضیح |
|---|---|---|
| `advertiser` | `ForeignKey` | ارتباط با مدل `Advertiser` |
| `title` | `CharField` | عنوان کمپین |
| `daily_budget` | `DecimalField` | سقف بودجه‌ی قابل‌مصرف در هر روز |
| `total_budget` | `DecimalField` | سقف بودجه‌ی کل کمپین |
| `start_date` | `DateField` / `DateTimeField` | تاریخ شروع اجرای کمپین |
| `end_date` | `DateField` / `DateTimeField` | تاریخ پایان اجرای کمپین |
| `status` | `CharField` با `choices` | وضعیت فعلی کمپین |
| `created_at` | `DateTimeField` | زمان ایجاد رکورد |

### ارتباط با Advertiser

هر `Advertiser` می‌تواند چندین کمپین ایجاد کند؛ اما هر کمپین تنها متعلق به یک تبلیغ‌دهنده است. به همین دلیل، رابطه‌ی بین `Campaign` و `Advertiser` از نوع **یک‌به‌چند** است.

```text
Advertiser 1 ──── * Campaign
```

بنابراین از `ForeignKey` استفاده می‌شود و استفاده از `OneToOneField` در این سناریو مناسب نیست.

### مدیریت بودجه

بودجه‌ی روزانه و بودجه‌ی کل در سطح کمپین نگهداری می‌شوند، نه در سطح تبلیغ‌دهنده.

این تصمیم معماری به دلیل تفاوت نیازهای بودجه‌ای کمپین‌های یک تبلیغ‌دهنده اتخاذ شده است. یک تبلیغ‌دهنده می‌تواند به‌صورت هم‌زمان چندین کمپین با اهداف و بودجه‌های متفاوت داشته باشد؛ برای مثال:

- کمپین معرفی محصول A با بودجه‌ی روزانه‌ی بالا
- کمپین تبلیغاتی محصول B با بودجه‌ی روزانه‌ی کمتر
- کمپین آزمایشی با بودجه‌ی کل محدود

اگر فیلد `daily_budget` در مدل `Advertiser` قرار می‌گرفت، عملاً بودجه‌ی روزانه برای تمام کمپین‌های آن تبلیغ‌دهنده یکسان در نظر گرفته می‌شد؛ در حالی‌که این رفتار با نیازهای واقعی یک پلتفرم تبلیغاتی سازگار نیست.

به دلیل ماهیت مالی این فیلدها، نوع داده‌ی مناسب برای آن‌ها `DecimalField` است. استفاده از `FloatField` ممکن است باعث خطاهای دقت محاسباتی شود و `IntegerField` نیز امکان ثبت مقادیر اعشاری را محدود می‌کند.

### وضعیت کمپین

فیلد `status` با استفاده از `choices` طراحی شده است تا چرخه‌ی عمر کمپین به‌صورت شفاف مدیریت شود. وضعیت‌های پیشنهادی عبارت‌اند از:

```text
ACTIVE     : فعال
PAUSED     : متوقف‌شده
COMPLETED  : پایان‌یافته
```

استفاده از `BooleanField` برای این نیاز کافی نیست؛ زیرا وضعیت یک کمپین صرفاً فعال یا غیرفعال نیست و ممکن است به دلیل پایان بازه‌ی زمانی یا اتمام بودجه، در حالت پایان‌یافته قرار گیرد.

## 4. مدل Ad

مدل `Ad` نماینده‌ی یک تبلیغ یا Creative است که زیرمجموعه‌ی یک کمپین محسوب می‌شود. هر کمپین می‌تواند چندین تبلیغ با محتوای متفاوت داشته باشد.

### فیلدها

| فیلد | نوع داده | توضیح |
|---|---|---|
| `campaign` | `ForeignKey` | ارتباط با مدل `Campaign` |
| `title` یا `headline` | `CharField` | عنوان یا متن اصلی تبلیغ |
| `image` | `ImageField` | تصویر تبلیغ |
| `destination_url` | `URLField` | مقصد کاربر پس از کلیک روی تبلیغ |
| `cpc` | `DecimalField` | هزینه‌ی هر کلیک |
| `is_active` | `BooleanField` | وضعیت فعال بودن تبلیغ |
| `created_at` | `DateTimeField` | زمان ایجاد رکورد |

### ارتباط با Campaign

هر کمپین می‌تواند شامل چندین تبلیغ باشد، اما هر تبلیغ تنها به یک کمپین وابسته است.

```text
Campaign 1 ──── * Ad
```

این ساختار امکان اجرای چند Creative مختلف در یک کمپین را فراهم می‌کند؛ برای مثال، یک کمپین می‌تواند چند نسخه‌ی متفاوت از تصویر، عنوان یا پیام تبلیغاتی را برای آزمایش و بهینه‌سازی عملکرد داشته باشد.

### تصویر تبلیغ

برای ذخیره‌سازی تصویر تبلیغ از `ImageField` استفاده شده است. استفاده از این فیلد در Django نیازمند نصب کتابخانه‌ی Pillow است:

```bash
pip install Pillow
```

همچنین تنظیمات مربوط به `MEDIA_URL` و `MEDIA_ROOT` باید در محیط توسعه و تولید به‌درستی پیکربندی شوند تا فایل‌های رسانه‌ای قابل ذخیره‌سازی و نمایش باشند.

### لینک مقصد

فیلد `destination_url` با `URLField` تعریف شده و باید اجباری باشد. تبلیغ بدون لینک مقصد، کاربرد اصلی خود را از دست می‌دهد؛ زیرا کاربر پس از کلیک باید به صفحه‌ی مشخصی مانند صفحه‌ی محصول، لندینگ‌پیج یا وب‌سایت تبلیغ‌دهنده هدایت شود.

استفاده از `URLField` به‌جای `CharField` باعث می‌شود Django اعتبار اولیه‌ی ساختار URL را بررسی کند.

### هزینه‌ی هر کلیک

فیلد `cpc` نشان‌دهنده‌ی هزینه‌ی هر کلیک تبلیغ است و مانند سایر مقادیر مالی باید از نوع `DecimalField` باشد تا دقت محاسبات مربوط به هزینه‌ها و گزارش‌گیری حفظ شود.

## 5. نام‌گذاری مدل‌ها

نام کلاس مدل‌ها در Django باید به‌صورت مفرد تعریف شود:

```python
class Campaign(models.Model):
    ...
```

و نه:

```python
class Campaigns(models.Model):
    ...
```

Django در رابط مدیریت و در برخی بخش‌های ORM، نام‌های جمع را به‌صورت خودکار تولید می‌کند. بنابراین، استفاده از نام مفرد برای کلاس مدل با استانداردهای Django و خوانایی کد سازگارتر است.

## 6. عملیات پایگاه داده و اعتبارسنجی اولیه

پس از تعریف مدل‌ها، مراحل زیر انجام شده است:

1. ایجاد migration برای مدل‌های جدید:

```bash
python manage.py makemigrations
```

2. اعمال migrationها روی پایگاه داده:

```bash
python manage.py migrate
```

3. ثبت مدل‌های `Campaign` و `Ad` در Django Admin

4. ایجاد داده‌ی آزمایشی شامل:
   - حداقل یک `Campaign`
   - حداقل یک `Ad` مرتبط با آن کمپین

این داده‌ی آزمایشی برای اطمینان از صحت رابطه‌ی بین مدل‌ها، ثبت صحیح رکوردها و بررسی نمایش آن‌ها در پنل مدیریت استفاده می‌شود.

## 7. کنترل نسخه و مدیریت کد

فایل‌های پروژه به مخزن GitHub منتقل شده‌اند و روند توسعه با کامیت‌های منظم ادامه پیدا می‌کند.

استفاده از Git و GitHub در این پروژه اهداف زیر را دنبال می‌کند:

### جلوگیری از از دست رفتن کد

در صورت بروز مشکل در سیستم، خرابی فایل‌ها یا حذف ناخواسته‌ی تغییرات، تاریخچه‌ی commitها امکان بازیابی نسخه‌های قبلی پروژه را فراهم می‌کند.

### ثبت تاریخچه‌ی توسعه

کامیت‌های کوچک، منظم و هدفمند نشان می‌دهند که پروژه به‌صورت مرحله‌به‌مرحله توسعه یافته است. این موضوع علاوه بر افزایش قابلیت نگهداری پروژه، برای بررسی روند توسعه و ارائه‌ی فنی پروژه نیز ارزشمند است.

نمونه‌ی مناسب از پیام کامیت:

```text
feat(campaigns): add Campaign and Ad models
```

یا:

```text
chore(campaigns): register campaign models in admin
```
