# فاز صفر: طراحی زیرساخت اولیه پروژه

قبل از شروع پیاده‌سازی منطق سیستم، اولین گام ایجاد یک زیرساخت توسعه‌ی قابل نگهداری و قابل توسعه بود. هدف این فاز صرفاً ایجاد یک پروژه Django نبود؛ بلکه فراهم کردن بستری بود که از همان ابتدای توسعه، مدیریت نسخه، مستندسازی و توسعه‌ی تدریجی پروژه را پشتیبانی کند.

## اهداف این فاز

در این مرحله زیرساخت اولیه پروژه با اهداف زیر ایجاد شد:

* ایجاد Repository برای مدیریت کد و مستندات
* راه‌اندازی محیط توسعه‌ی مستقل
* ایجاد ساختار اولیه پروژه Django
* آماده‌سازی پروژه برای توسعه‌ی تدریجی و Version Control

---

# تصمیم‌های طراحی

## Repository به عنوان منبع اصلی پروژه

از ابتدای توسعه، تمامی کدها، مستندات و تاریخچه تغییرات در یک Repository مستقل در GitHub نگهداری می‌شوند. این تصمیم باعث می‌شود تغییرات پروژه قابل ردیابی باشند و مستندات و کد در کنار یکدیگر تکامل پیدا کنند.

در این پروژه، Repository تنها محل نگهداری کد نیست؛ بلکه مستندات معماری، تصمیم‌های طراحی و Roadmap توسعه نیز بخشی از آن محسوب می‌شوند.

---

## جداسازی محیط توسعه

تمام وابستگی‌های پروژه در یک **Virtual Environment** مستقل نگهداری می‌شوند تا محیط اجرای پروژه از سایر پروژه‌های Python روی سیستم جدا باشد.

```text
System Python
    │
    ├── Project A Environment
    ├── Project B Environment
    └── Mini-AdTech-Platform Environment
```

این رویکرد وابستگی‌های پروژه را ایزوله کرده و بازتولید محیط توسعه را روی سیستم‌های دیگر ساده‌تر می‌کند.

---

## مدیریت وابستگی‌ها

یکی از تصمیم‌های این پروژه، جداسازی **کد منبع** از **محیط اجرا** است.

به همین دلیل، Virtual Environment بخشی از Repository نیست و تنها وابستگی‌های موردنیاز پروژه ثبت می‌شوند. این وابستگی‌ها از طریق فایل `requirements.txt` قابل بازسازی هستند و هر توسعه‌دهنده می‌تواند محیط اجرای مستقل خود را ایجاد کند.

```text
GitHub Repository
       │
       ├── Source Code
       ├── requirements.txt
       └── .gitignore

Development Environment
       │
       └── Virtual Environment
```

این ساختار باعث می‌شود Repository مستقل از سیستم‌عامل یا محیط توسعه‌ی افراد باقی بماند.

---

## فلسفه استفاده از .gitignore

فایل `.gitignore` بخشی از معماری مدیریت Repository است و مشخص می‌کند کدام فایل‌ها یا پوشه‌ها نباید تحت Version Control قرار بگیرند.

در این پروژه، فایل‌ها و پوشه‌هایی مانند موارد زیر از Repository حذف شده‌اند:

* `.venv/`
* `.env`
* `__pycache__/`
* `*.pyc`

دلیل این تصمیم، جلوگیری از ورود فایل‌های وابسته به محیط توسعه، فایل‌های موقت و اطلاعات حساس به مخزن کد است. این کار حجم Repository را کاهش می‌دهد، از انتشار ناخواسته اطلاعات محرمانه جلوگیری می‌کند و بازتولید محیط توسعه را ساده‌تر می‌سازد.

---

# خروجی این فاز

در پایان این مرحله، زیرساخت اولیه پروژه آماده شد و بستر لازم برای توسعه‌ی منطق کسب‌وکار فراهم گردید.

```text
GitHub Repository
       │
       ├── README.md
       ├── .gitignore
       ├── Django Project
       └── Git History
```

در این مرحله تمرکز بر ایجاد یک پایه‌ی پایدار برای توسعه بود؛ بنابراین از ورود به پیاده‌سازی منطق تبلیغات یا طراحی مدل‌های دامنه خودداری شد. این رویکرد امکان توسعه‌ی تدریجی، مستندسازی مستمر و مدیریت تغییرات را در مراحل بعدی فراهم می‌کند.

---

# فاز بعدی

در فاز بعد، طراحی مدل دامنه آغاز می‌شود و موجودیت‌های اصلی سیستم شامل **Advertiser**، **Publisher**، **Campaign** و سایر اجزای هسته‌ی پلتفرم تبلیغاتی معرفی و مدل‌سازی خواهند شد.
