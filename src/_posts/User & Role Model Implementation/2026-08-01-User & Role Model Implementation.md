# پیاده‌سازی مدل‌های کاربران و نقش‌ها

در این فاز، تصمیم‌های معماری مربوط به مدل `User` و نقش‌های `Advertiser` و `Publisher` به مدل‌های Django تبدیل شدند.

هدف این مرحله، ایجاد مدل‌های دامنه‌ای است که ضمن حفظ ارتباط با سیستم احراز هویت Django، اطلاعات اختصاصی هر نقش را به‌صورت مستقل نگهداری کنند.

---

## ساختار مدل‌ها

برای مدیریت منطق مرتبط با کاربران، یک Django App با نام `accounts` ایجاد شد.

مدل‌های اصلی این فاز:

```text
User
 ├── Advertiser
 └── Publisher
```

هر دو مدل `Advertiser` و `Publisher` با استفاده از `OneToOneField` به مدل پیش‌فرض `User` متصل شده‌اند:

```python
user = models.OneToOneField(
    User,
    on_delete=models.CASCADE
)
```

این ساختار امکان استفاده از سیستم احراز هویت Django را در کنار نگهداری اطلاعات اختصاصی هر نقش فراهم می‌کند.

در نتیجه، اطلاعات عمومی و احراز هویت در `User` قرار دارد و اطلاعات مرتبط با کسب‌وکار تبلیغ‌دهنده یا ناشر در مدل اختصاصی همان نقش نگهداری می‌شود.

---

# وضعیت و چرخه‌ی عمر حساب

هر دو مدل `Advertiser` و `Publisher` دارای وضعیت‌های زیر هستند:

* `is_active` — مشخص می‌کند حساب در حال حاضر فعال است یا خیر.
* `is_valid` — وضعیت اعتبارسنجی حساب را مشخص می‌کند.
* `created_at` — زمان ایجاد رکورد را نگهداری می‌کند.

برای `created_at` از `DateTimeField(auto_now_add=True)` استفاده شده است تا زمان ایجاد رکورد به‌صورت خودکار ثبت شود.

تفکیک `is_active` و `is_valid` این امکان را فراهم می‌کند که وضعیت عملیاتی حساب از وضعیت اعتبارسنجی آن مستقل باشد.

---

# تصمیم طراحی: نوع داده برای مقادیر مالی

یکی از تصمیم‌های مهم در پیاده‌سازی مدل `Advertiser`، انتخاب نوع داده برای `wallet_balance` است.

مقدار موجودی کیف پول یک داده‌ی مالی است و دقت محاسبات آن اهمیت دارد. بنابراین به‌جای `IntegerField` یا `FloatField` از `DecimalField` استفاده شده است:

```python
wallet_balance = models.DecimalField(
    max_digits=12,
    decimal_places=2
)
```

استفاده از `DecimalField` امکان نگهداری مقادیر اعشاری با دقت مشخص را فراهم می‌کند و از مشکلات مربوط به نمایش و محاسبه‌ی اعداد اعشاری با `Float` جلوگیری می‌کند.

این تصمیم در آینده برای سایر مقادیر مالی مانند:

* Campaign Budget
* CPC
* Click Cost
* Publisher Revenue
* Transaction Amount

نیز اهمیت خواهد داشت.

بنابراین انتخاب نوع داده‌ی مالی در این مرحله بخشی از طراحی زیرساخت Billing آینده محسوب می‌شود.

---

# تصمیم طراحی: اطلاعات بانکی

اطلاعاتی مانند شماره کارت یا شماره شبا به‌عنوان مقدار عددی مدل نمی‌شوند.

دلیل این تصمیم این است که این داده‌ها:

1. برای عملیات ریاضی استفاده نمی‌شوند.
2. ممکن است دارای صفر ابتدایی باشند.
3. محدودیت‌های عددی دیتابیس برای چنین داده‌ای کاربردی ندارد.
4. ماهیت آن‌ها **Identifier** است، نه مقدار عددی.

بنابراین چنین اطلاعاتی باید به‌صورت رشته‌ای نگهداری شوند؛ برای مثال:

```python
bank_card_number = models.CharField(max_length=16)
```

البته این تصمیم صرفاً مربوط به نوع داده است. در یک سیستم Production، اطلاعات مالی حساس نیازمند کنترل دسترسی، محافظت از داده و ملاحظات امنیتی بیشتری خواهند بود.

---

# Naming Convention

نام فیلدهای مدل‌ها بر اساس قرارداد `snake_case` انتخاب شده‌اند:

```text
Company        → company
Wallet_Balance → wallet_balance
Is_Active      → is_active
```

این انتخاب مطابق Conventionهای رایج Python و Django است و باعث می‌شود کد، Queryها و APIهای پروژه با الگوی یکسانی توسعه پیدا کنند.

---

# Category Modeling

برای `Advertiser` و `Publisher` از مقدار متنی آزاد برای دسته‌بندی استفاده نشده است. هر مدل مجموعه‌ی `choices` مخصوص خود را دارد.

برای مثال:

```python
CATEGORY_CHOICES = [
    ("insurance", "Insurance"),
    ("ecommerce", "E-commerce"),
    ("tech", "Technology"),
]
```

و:

```python
category = models.CharField(
    max_length=50,
    choices=CATEGORY_CHOICES
)
```

استفاده از `choices` باعث می‌شود مقادیر مجاز کنترل شوند و از ایجاد داده‌های ناسازگار در دیتابیس جلوگیری شود.

---

## تفکیک Category و Content Category

اگرچه هر دو مدل دارای مفهوم دسته‌بندی هستند، این دو فیلد یک مفهوم واحد را بیان نمی‌کنند.

در `Advertiser`:

```text
category
```

حوزه‌ی فعالیت کسب‌وکار تبلیغ‌دهنده را مشخص می‌کند؛ مانند:

```text
Insurance
E-commerce
Technology
```

در `Publisher`:

```text
content_category
```

موضوع محتوای وب‌سایت یا اپلیکیشن ناشر را مشخص می‌کند؛ مانند:

```text
News
Sports
Entertainment
Technology
```

این دو مفهوم عمداً با دو مجموعه‌ی مستقل مدل شده‌اند، زیرا یکسان بودن آن‌ها از نظر دامنه‌ی کسب‌وکار الزامی نیست.

برای مثال، یک Publisher می‌تواند وب‌سایتی با محتوای `Entertainment` داشته باشد، در حالی که Advertiserهای سیستم در حوزه‌هایی مانند `Insurance` یا `E-commerce` فعالیت می‌کنند.

این تفکیک در مراحل بعدی می‌تواند برای طراحی قابلیت‌هایی مانند **Content-based Targeting** نیز مورد استفاده قرار گیرد.

---

# Django Admin

مدل‌های `Advertiser` و `Publisher` در Django Admin ثبت شده‌اند تا در فازهای اولیه‌ی توسعه امکان مدیریت و بررسی داده‌های مدل‌ها وجود داشته باشد.

استفاده از Django Admin در این مرحله به‌عنوان یک ابزار داخلی برای مدیریت داده و اعتبارسنجی اولیه‌ی مدل‌ها در نظر گرفته شده است و بخشی از رابط کاربری نهایی سیستم محسوب نمی‌شود.

---

# Validation اولیه

پس از ایجاد مدل‌ها، Migrationهای مربوط به ساختار جدید اعمال شدند و نمونه‌های اولیه‌ی `Advertiser` و `Publisher` برای بررسی رفتار مدل‌ها ایجاد شدند.

این مرحله برای اطمینان از موارد زیر انجام شد:

* ایجاد صحیح روابط `OneToOne`
* اعمال صحیح Defaultها
* ثبت خودکار `created_at`
* ذخیره‌ی مقادیر `DecimalField`
* اعمال `choices`
* دسترسی صحیح مدل‌ها از طریق Django Admin

# Architectural Summary

تصمیم‌های اصلی این فاز را می‌توان به شکل زیر خلاصه کرد:

| موضوع                      | تصمیم                                     |
| -------------------------- | ----------------------------------------- |
| Authentication             | استفاده از مدل پیش‌فرض `User`             |
| Role Modeling              | مدل مستقل برای `Advertiser` و `Publisher` |
| ارتباط با User             | `OneToOneField`                           |
| وضعیت حساب                 | `is_active` و `is_valid`                  |
| زمان ایجاد                 | `DateTimeField(auto_now_add=True)`        |
| مقادیر مالی                | `DecimalField`                            |
| اطلاعات بانکی              | `CharField`                               |
| Naming Convention          | `snake_case`                              |
| Advertiser Category        | `choices` مستقل                           |
| Publisher Content Category | `choices` مستقل                           |
| مدیریت اولیه               | Django Admin                              |

در این مرحله، مدل‌های کاربران پایه‌ی لازم برای توسعه‌ی سایر موجودیت‌های دامنه را فراهم می‌کنند.

در فازهای بعدی، `Advertiser` به موجودیت‌هایی مانند `Campaign` و `Wallet` متصل خواهد شد و `Publisher` نیز به ساختار `Website` و `AdSlot` متصل می‌شود. این روابط، پایه‌ی شکل‌گیری چرخه‌ی اصلی سیستم یعنی **Ad Serving → Impression → Click → Billing** خواهند بود.
